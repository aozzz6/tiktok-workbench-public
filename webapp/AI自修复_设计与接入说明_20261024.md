# AI 自修复 · 设计与接入说明（2026-10-24）

> 范围：在既有「一键修复」上增加 AI 模型接口，让模型参与**诊断 / 选动作 / 失败归因**。
> 一句话边界：**AI 只做决策，不做执行** —— 它不能写台账、不能跑命令、不能指定路径。

---

## 1. 接口调用方式与触发条件

### 1.1 新增端点

| 方法 | 路径 | 用途 | 关键入参 / 出参 |
|---|---|---|---|
| GET | `/api/ai/models` | 模型清单（key 一律掩码）+ 动作白名单 + 配置来源 | 出：`models[]`（id/name/vendor/style/key_masked/cooldown_s/is_default）、`actions[]`、`sources` |
| GET | `/api/ai/config` | 读 AI 配置（不含 key） | 出：`enabled/model/fallbacks/timeout_s/预算/proxy/available` |
| POST | `/api/ai/config` | 改配置（白名单字段落盘 + 数值夹紧） | 入：`{model, fallbacks, enabled, timeout_s, max_calls_per_round, max_tokens_per_round, temperature, proxy}` |
| POST | `/api/ai/test` | 探活：真发一条极短请求，验「连得上 + 出 JSON」 | 入：`{model?}`；出：`{ok, model, style, latency_ms, json_ok, error?}` |
| GET | `/api/ai/calls` | 调用审计（只含元数据） | 入：`limit`（1–200） |
| POST | `/api/repair/start` | 一键修复（本次新增 `use_ai` / `model`） | 入：`{use_ai?, model?, ids?, days?, retry?, timeout?}` |
| GET | `/api/repair/status` | 进度（本次新增 `ai` 块与每项 `ai` 判定） | 出：`ai{phase,model,degraded,error,judged,attributed,requests,calls,tokens}` |

### 1.2 触发条件（明确到可核对）

| 场景 | 是否调用模型 | 说明 |
|---|---|---|
| 点「一键修复」，勾了「AI 诊断」 | ✅ 先诊断（1 次批量）+ 失败项归因（≤4 次/轮） | 主力路径 |
| 点「一键修复」，未勾「AI 诊断」 | ❌ 完全不调用 | 纯规则模式，与改造前一致 |
| 点「测试」 | ✅ 1 次极短探活 | 用户主动，成本≈50 token |
| 定时/自动化日更 | ❌ 不自动接 AI | 避免无人值守时消耗 token；需要时可显式加参数 |
| AI 关闭 / 无 key / 冷却中 / 预算耗尽 | ❌ 自动跳过 | 直接走规则结论，并在 `ai.degraded=true` + `error` 里说明 |
| 单项目执行失败 | ✅ 归因 1 次（若还有预算） | `MAX_ATTR_PER_ROUND = 4` |

**前置拦截**：`use_ai=true` 但没有任何可用模型 → `/api/repair/start` 返回 **400** 并写明原因（不静默降级，避免用户以为 AI 生效了）。

## 2. 可自主修复的问题类型与范围

模型**只能在 6 个白名单动作里挑一个**，动作清单是代码里的单一事实源（`ai_repair.ACTIONS`）：

| 动作 | 执行的真实命令 | 允许覆盖的规则类型 |
|---|---|---|
| `rerun_collect` | `daily_batch.py --accounts X`（全链） | collect |
| `sync_ledger` | `post_update_flow.py --accounts X` | ledger、collect |
| `retry_transcribe` | `pipeline.py --steps s5_transcribe --no-resume` + 台账同步 | transcribe、collect |
| `extract_products` | `extract_products.py --account X` | products、collect |
| `skip` | 不执行 | 任意 |
| `manual` | 不执行，标「需人工」 | 任意 |

覆盖范围：采集断链、转写缺失、商品未提取、台账未入账。

**明确不做**：
- 不改台账结构、不删文件、不执行模型生成的任何命令或路径（输出结构里根本没有这类字段）；
- 不做翻译（本地无 LLM 写 N 列就是造假）；
- 不处理「数据本身错」（标题抓错、列错位）→ 一律 `manual`；
- 不碰停用账号（`active=false` / `ledger_skip`）。

## 3. 多模型适配与统一调用

上层只调一个函数：`llm.chat(messages, model=None, json_mode=…)`。三种 API 风格在 `llm.py` 内被抹平：

| 风格 | 路由条件 | 端点 | 覆盖的厂商 / 服务 |
|---|---|---|---|
| `openai` | 默认 | `{url}/chat/completions` | OpenAI、DeepSeek、Moonshot/Kimi、智谱 GLM、通义 DashScope 兼容、豆包 Ark、MiniMax、SiliconFlow、OpenRouter、Groq、Together、xAI、Ollama、vLLM、LM Studio、llama.cpp，以及各类中转站 |
| `anthropic` | `vendor`/`id`/`url` 含 anthropic/claude，或 `api_style:"anthropic"` | `{url}/v1/messages` | Claude 原生 |
| `gemini` | 含 gemini/generativelanguage，或 `api_style:"gemini"` | `{url}/v1beta/models/{id}:generateContent` | Google 原生 |

统一处理（都是实测踩过的坑）：
- 响应结构差异 → `_extract()` 抹平成 `{text, usage}`；
- `max_tokens` vs `max_completion_tokens`（新版 OpenAI 推理模型）→ 400 时自动换字段重试一次；
- 空正文（推理模型把预算全花在 reasoning）→ 加倍预算重试；
- `429/5xx/超时` → 指数退避重试（408/409/425/429/500/502/503/504）；
- `400/401/403/404` → **不重试**（重试也没用），直接换下一个模型；
- 网关 200 + HTML → 当解析失败处理；
- JSON 输出 → 5 级容错（围栏 / 前后说明 / 尾逗号 / 截取大括号 / 截断抢救）。

## 4. 模型配置与切换机制

三层，从低到高覆盖：

1. **`~/.workbuddy/models.json`**（现有，裸数组或 `{models:[]}`）
   ```json
   [{ "id": "deepseek-flash", "name": "DeepSeek V4.1 Flash", "vendor": "deepseek",
      "url": "https://api.deepseek.com/v1", "apiKey": "sk-…",
      "supportsImages": true, "supportsToolCall": true }]
   ```
   判定可用：有 `url` 且（有 `apiKey` 或 是本地地址）。缺 key 的远端条目直接忽略。

2. **`webapp/data/ai_config.json`**（项目级偏好，由 `/api/ai/config` 写）
   ```json
   { "enabled": true, "model": "", "fallbacks": ["deepseek-flash", "TM ·Auto"],
     "timeout_s": 90, "max_calls_per_round": 12, "max_tokens_per_round": 40000,
     "temperature": 0.2, "proxy": "" }
   ```

3. **环境变量**（临时覆盖，优先级最高）
   `WB_AI_DISABLED=1` 关闭；`WB_AI_MODEL` 指定模型；`WB_AI_BASE`+`WB_AI_KEY` 临时接一套而不改文件；`WB_AI_PROXY` 走代理。

**切换方式**：
- 界面：待接管面板的模型下拉（「自动选模型」= 按 `model → fallbacks → 内置偏好` 挑）；
- API：`POST /api/ai/config {"model": "…"}`；
- 单次：`POST /api/repair/start {"use_ai": true, "model": "…"}`（只影响这一次修复）。

**稳定性保护**：同一模型连续失败 3 次 → 冷却 120s（界面标「冷却中」），期间自动跳到回退链的下一项；每轮有 `max_calls_per_round` / `max_tokens_per_round` 双上限。

> **R3 整改（2026-10-24 独立验收）**：`max_calls_per_round` 现在按**每一次物理 HTTP 请求**计数，
> 覆盖同模型重试、空正文重问、回退链、`chat_json` 的「只输出 JSON」二次追问；请求在发出前
> 先预检，超预算的请求一次都不会发；`usage` 按服务端每次响应累计。
> **口径说明**：`requests` 是真实请求数（界面显示「模型请求 N 次」）；`tokens` 是服务端回报
> 的累计值；token 上限按「输出上限预留 + 实际回报」估算，**不保证精确费用封顶**，只用于防失控。

## 5. 修复失败 / 异常时的回退与人工介入

### 5.1 AI 层回退矩阵

| 异常 | 行为 |
|---|---|
| AI 关闭 / 无模型 / 全部冷却 | `degraded=true`，**直接按规则结论执行**，`error` 写明原因 |
| 调用超时 / 网络失败 | 同模型退避重试 → 换 fallback → 全失败则降级 |
| 输出不是合法 JSON | 追加「只输出 JSON」再问 1 次 → 仍失败则降级 |
| 动作不在白名单 / 与缺口类型不兼容 / id 不存在 | **丢弃该条建议**，该项保留规则动作 |
| 置信度 < 0.55 | 不采纳，保留规则动作，记 `applied=false`、`needs_human=true` |
| 预算耗尽（按物理请求/token 累计判断） | 剩余项不再调模型，直接规则模式；超预算的请求不会发出 |
| 模型判 `manual` | 该项不执行，标「AI 判定（转人工）：理由」，进跳过汇总 |

**关键原则**：AI 的任何故障都不阻断修复本身 —— 最坏情况退回改造前的规则模式。

### 5.2 人工介入
- 完成汇总里「跳过」组默认展开，每条写明「为什么没修」；
- 失败项给 `exit 码 + 日志尾 + AI 归因（类别/根因/是否值得重试/下一步建议）」；
- 「重试失败项（N）」：重新扫描 → 按 `kind+account` 映射新 id → 只提交失败项（AI 建议 `retry_worth=false` 时更适合先去改配置）；
- 归因类别：`network / auth / quota / timeout / empty / gate / schema / permission / unknown`。

## 6. 输出修复结果与验证方式

### 6.1 结果结构（`GET /api/repair/status`）
```json
{
  "total": 3, "done": 3, "percent": 100,
  "counts": { "ok": 1, "failed": 1, "skipped": 1 },
  "ai": { "enabled": true, "phase": "done", "model": "deepseek-flash",
          "degraded": false, "error": "", "judged": 2, "attributed": 1,
          "requests": 2, "calls": 2, "tokens": 648, "truthful": true },
  "items": [{
    "id": "rp04", "kind": "ledger", "account": "example_account_033", "status": "failed",
    "detail": "台账同步失败（exit=1）：verify 发现「商品链接」列缺失 ｜ AI 归因：… → …",
    "ai": { "action": "sync_ledger", "action_label": "台账同步", "confidence": 0.88,
            "applied": true, "reason": "数据已在磁盘，只差入账",
            "attribution": { "category": "schema", "cause": "…", "retry_worth": false,
                             "suggestion": "…" } }
  }]
}
```
`truthful=false` 是重要信号：表示本轮 AI 已降级，结论完全来自规则引擎。

### 6.2 结果验证（不只信退出码）
1. **退出码**：`exit != 0` 即失败；
2. **空跑护栏**：`< 2s` 结束判「疑似空跑」（`pipeline_state` 不带 `no_resume` 会秒退 exit=0）；
3. **业务复核**：采集项跑完回头查待接管队列是否还有该账号；转写项再数一次音频/转写文件数；
4. **AI 归因**：失败时给出类别与是否值得重试（仅作建议，不改变判定）。

### 6.3 可审计性
- `webapp/data/ai_calls.jsonl`：每次调用的模型/风格/用途/耗时/token/成败/错误摘要（**不记 prompt 全文、不记 key**），超过 2MB 自动轮转；
- 界面「测试」按钮可随时验证连通；
- 统计：`judged / requests（物理模型请求数） / tokens / attributed` 全在进度区可见；`calls` 与 `requests` 同义，保留是为了兼容旧前端。

### 6.4 验收清单（本次实测）
| 项 | 结果 |
|---|---|
| 真实模型探活 `deepseek-flash` | ✅ 858ms，JSON 可用，61+25 token |
| 真实 AI 诊断（真实计划，不执行） | ✅ 1084ms，648 token，判定 `rerun_collect` 置信度 0.95，理由与日志一致 |
| `ai_llm`（路由/重试/熔断/审计/JSON 容错） | ✅ 19/19 |
| `ai_repair`（白名单/降级/预算/归因） | ✅ 13/13 |
| `ai_api`（端点契约/400 拦截/无 key 泄露） | ✅ 10/10 |
| `repair_ai`（AI 改动作/转人工/降级/归因） | ✅ 7/7 |
| `ai_ui`（开关/下拉/测试/AI 标签/降级提示） | ✅ 14/14 |
| 既有 `repair_*` 与全量 js 套件 | ✅ 全绿（py 见当日日志） |

## 附：为什么这样切分（安全论证）

1. **模型没有执行面**：输出只有枚举 `action` + 置信度 + 理由，没有命令、路径、SQL 字段。
2. **动作白名单 + 类型兼容矩阵**：即使模型被提示注入，也只能在"重跑/同步/转写/提取/跳过/转人工"里选，且必须与缺口类型匹配。
3. **参数不可信**：账号来自本地计划（`validate_account_name` 已在 plan 阶段校验），AI 不能新增账号；`days/retry/timeout` 由会话参数决定，AI 无权修改。
4. **单一写者不变**：台账仍只由 `post_update_flow` / `daily_batch` 写入，AI 与前端都不能直接写表。
5. **可降级**：从配置、网络、协议、解析到语义，每一层失败都退回规则引擎，修复流程不断。
